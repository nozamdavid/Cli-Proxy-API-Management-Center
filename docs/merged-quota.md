# Merged quota summary

The quota page keeps its existing provider navigation and cards. Its summary calls the authenticated management endpoint `GET /v8/management/quota/aggregate` for Antigravity and Codex. The backend caches this response for 90 seconds; the summary refresh button sends `?refresh=true` to bypass that cache. Other supported providers use their existing quota adapters.

The aggregate endpoint must return the documented account fields, including Antigravity groups and buckets and Codex quota signals. The panel only displays `X-Codex-*` signals, treats missing or failed data as unavailable, and leaves empty provider arrays valid. The connected backend must provide this route before deploying a panel that uses the merged summary.

## Pooled time-series charts

Each chart pool represents one provider and one quota window. Antigravity groups and buckets stay separate, as do adapter windows with different limits or periods. The headline adds each known account's remaining percentage and assigns 100 percentage points of capacity per contributing account; provider plan labels do not change that capacity. Unknown, failed, and disabled accounts do not contribute, and the chart reports coverage.

The panel keeps graph snapshots in browser `localStorage` so it can draw the last successful graph view synchronously while the page refreshes. A snapshot contains normalized pool labels and provider types, numeric remaining values and reset instants, source observation times, counts, and opaque pool, contributor, and membership IDs. Its scope is a fingerprint of the normalized hub and authenticated management identity. Raw account names, filenames, email addresses, tokens, and management keys are not stored. Snapshots expire after 24 hours and are bounded to 48 pools, eight identity scopes, and 512 KiB; logout and an explicit hub or credential switch remove the previous identity's entry. A temporary connection or refresh failure retains the useful snapshot. Browser storage errors fall back to a bounded in-memory cache.

The selected graph snapshot is hydrated before the first network await. It remains visible during automatic, manual, and page file-list refreshes with a cached/refreshing label. A failed refresh keeps the cached graph and shows an error state; a successful refresh replaces it. Once the latest authoritative file list is available, cached contributors for deleted or disabled files are removed from the displayed pools. Cache hydration never appends a history sample or supplies an observation timestamp for burn calculations.

Successful graph snapshots also include each pool's bounded forecast points and its original burn, reset, and empty-time metadata, scoped to the same pool capacity, membership, and source observation. A warm cache renders those frozen points and statistics as a dated cached estimate while the next refresh runs. Forecast points never enter recorded history; older snapshots without a forecast still show the recorded graph without inventing an estimate.

Each provider's selected graph pool is saved as an opaque pool ID under the same hub and management identity scope. Antigravity defaults to the `Gemini Models` `gemini-weekly` weekly bucket when no saved selection is available.

Graph colors can be customized per provider. Overrides use six-digit hex colors and are stored under the same opaque hub and management identity scope; reset removes that provider's override and restores the existing theme palette.

Historical points remain in their existing separate local cache, capped at 2,016 points and 14 days. New v2 history keys use the same opaque hub and management identity scope as graph snapshots, plus the pool window and contributor membership signature. Pre-auth-scope v1 entries are not reused or migrated. Membership is checked when a pool returns. During temporary adapter loading, up to 128 visible or recently used pool histories are retained in memory for the current identity. Fresh provider observations are appended to history only from actual source timestamps after all contributors in a pool are updated; graph cache hydration never creates an observation. Adapter observations must finish within 60 seconds of one another; the sample uses the median actual completion time. Antigravity samples use the aggregate response's `generated` timestamp. The panel does not fill gaps with generated samples or reuse a stale cached value as a new observation. A new pool says “History starts with first refresh” until its first observation is captured. Burn rate requires at least three comparable observations spanning ten minutes; comparisons across a known reset, a membership change, a large gap, or a quota increase are discarded. Without enough history, a dashed reset-only estimate assumes no additional use. With a measured rate, the forecast applies that recent pooled rate and known per-account resets, caps the total at pool capacity, and never invents recurring resets. Reset jumps use the current observed balance for the account, so they are estimates rather than provider guarantees. Unknown reset times produce no reset jump. The chart's expandable data table lists at most the latest 100 recorded and earliest 100 projected points for the selected pool.

Keep the existing quota sidecar in place until a deployed backend and panel have been verified together. Confirm the route authenticates normally, disabled accounts are listed but are not fetched, Antigravity sums use only accounts exposing each bucket, Codex signals and model quotas appear, empty signals display as unavailable, and automatic/manual refresh behaves as expected. Retire the sidecar only after those checks pass against the deployed versions.
